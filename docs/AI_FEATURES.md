# AI_FEATURES.md

本项目**目前有 AI 功能**,集中在 `api/` 目录下的 4 个接口,全部调用同一个模型。前端从不直接持有或调用 API key——所有 AI 调用都经过 Vercel serverless 函数中转,密钥只存在服务器端环境变量里。

## 1. 使用的模型

**`claude-sonnet-4-6`**(写死在 `api/_lib/claude.ts` 里的常量 `MODEL`,4 个接口共用同一份调用逻辑)。

每次调用参数:
- `max_tokens: 1024`(输出上限,4 个接口都一样)
- `system`:每个接口各自的系统提示词(见下文)
- `messages`:只有一条 `role: 'user'` 消息,内容是用户输入(文字,或"文字+图片"的组合)

## 2. 输出格式约定与解析方式

4 个接口的系统提示词里都明确要求"只输出 JSON 本身,不要前言、不要 Markdown 代码块标记"。但实际调用中 AI 仍可能带上 ` ```json ` 这样的代码块标记,所以前端统一在 `stripJsonFences()` 里做了一次清洗:

```
text.replace(/```json|```/g, '').trim()
```

清洗后再 `JSON.parse()`。**如果解析仍然失败,不会静默丢弃**——原始文字会被挂在错误对象的 `rawText` 字段上,一路传回前端展示给用户,方便用户知道 AI 到底说了什么、手动处理。

## 3. 逐接口:Prompt 全文 + 输入输出格式

### 3.1 `POST /api/parse-workout` —— 自然语言训练记录解析

**系统提示词全文**:

> 你是一个健身记录解析助手。将用户输入的一段中文训练描述(可能来自语音转写)解析为结构化 JSON。
> 只输出 JSON 本身,不要任何前言、解释或 Markdown 代码块标记(不要用 \`\`\`)。
>
> JSON 格式:
> ```
> {
>   "strength": [
>     {
>       "name": "动作名称",
>       "sets": [{ "weight": 数字, "reps": 数字, "done": true }],
>       "note": "识别不出的原文片段,没有则省略",
>       "uncertain": ["描述没把握的地方,没有则省略"]
>     }
>   ],
>   "cardio": [
>     {
>       "type": "跑步/单车/椭圆机/游泳/跳绳/划船机/快走",
>       "minutes": 数字,
>       "distance": 数字或null,
>       "avgHr": 数字或null,
>       "intensity": "low" | "mid" | "high",
>       "note": "识别不出的原文片段,没有则省略",
>       "uncertain": ["描述没把握的地方,没有则省略"]
>     }
>   ]
> }
> ```
>
> 规则:
> - 不要输出热量(estKcal),热量由程序用 MET 公式计算,不需要你估算。
> - 重量单位统一转换成 kg 的纯数字。"公斤"、"kg"、"KG"、"千克" 都视为 kg;如果原文是磅(lb/斤),按常识换算成 kg。
> - "4 组 8 次" 这类简写要展开成 4 个独立的 set,每个 { reps: 8 }。如果每组次数不同(如"前三组 8 次最后一组 6 次"),按实际展开,不要都填成一样。
> - sets 里的 done 一律填 true(用户在描述已完成的训练)。
> - intensity 没有明确提到时,默认 "mid"。
> - 遇到不确定的地方(比如重量、次数、强度是靠推测得出的),在该条目的 uncertain 数组里写清楚是什么不确定,不要静默地编造数字。
> - 完全无法归类到某个动作/项目的原文片段,放进对应条目最相关的 note 字段;如果整体都无法识别,返回 { "strength": [], "cardio": [] }。
> - 不要猜测原文没有提到的信息。

**输入**:纯文字(用户描述的一段训练内容)。
**输出**:`strength[]` + `cardio[]`,字段见上。**刻意不让 AI 估算热量**——这是一个明确的产品决策,热量由 `src/lib/met.ts` 里的 MET 公式在前端计算,理由是 MET 公式确定、免费、瞬时,AI 估算反而不稳定还要花 token。

**关键设计**:AI 解析出的动作如果和当天已有的同名动作重复,前端会把新的 sets 合并进已有记录,而不是重复新建一条(方便"计划里已导入卧推,又用语音补充说多做了一组"这种场景)。

### 3.2 `POST /api/parse-meal` —— 自然语言饮食记录解析

**系统提示词全文**:

> 你是一个饮食记录解析助手。将用户输入的一段中文饮食描述解析为结构化 JSON,并估算每一种食物的营养数据。
> 只输出 JSON 本身,不要任何前言、解释或 Markdown 代码块标记(不要用 \`\`\`)。
> JSON 格式:
> ```
> {
>   "items": [
>     {
>       "name": "食物名称",
>       "grams": 数字,
>       "kcal": 数字,
>       "protein": 数字,
>       "carbs": 数字,
>       "fat": 数字,
>       "confidence": "high" | "mid" | "low"
>     }
>   ]
> }
> ```
> 一段描述里可能包含多种食物,请拆分为多个 item。grams 按常识估算份量。
> confidence 表示你对这一项估算的把握程度:描述具体(如写明重量、品牌)用 "high",描述模糊用 "low"。
> 如果完全无法识别为食物,返回 { "items": [] }。

**输入**:纯文字。**输出**:`items[]`,每项含名称、克数、四大营养素、置信度。

---

### 3.3 `POST /api/analyze-photo` —— 食物照片识别

**系统提示词全文**:

> 你是一个食物照片识别助手。识别图片中的每一种食物,并估算营养数据。
> 只输出 JSON 本身,不要任何前言、解释或 Markdown 代码块标记(不要用 \`\`\`)。
> JSON 格式:
> ```
> {
>   "items": [
>     {
>       "name": "食物名称",
>       "grams": 数字,
>       "kcal": 数字,
>       "protein": 数字,
>       "carbs": 数字,
>       "fat": 数字,
>       "confidence": "high" | "mid" | "low"
>     }
>   ]
> }
> ```
> 图中可能有多种食物,请拆分为多个 item。grams 按视觉份量常识估算。
> confidence 表示你对这一项估算的把握程度,看不清或难以判断分量时用 "low"。
> 如果图片中无法识别出食物,返回 { "items": [] }。

**输入**:一段固定的文字指令("请识别图中的每一种食物并估算营养数据。")+ 一张 base64 编码的图片(`image/jpeg`、`png`、`webp` 或 `gif`,不合法时按 `jpeg` 处理)。
**输出**:同 3.2。

**图片预处理**(在前端做,不在这个接口里):上传前先压缩到长边不超过 1024px、JPEG 质量 0.7,再转 base64。界面上会固定提示一句"拍照估算是粗略参考,和实际可能有明显差距",低置信度的项目在界面上用浅黄色底标出来提醒用户核对。

---

### 3.4 `POST /api/recalc-meal` —— 按备注重新估算

**系统提示词全文**:

> 你是一个饮食记录修正助手。用户会给你一份原始的食物估算列表(JSON)和一段备注文字,备注描述了实际情况和估算的差异。
> 根据备注调整每一项食物的克数和营养数据,没有被备注提到的项目保持不变。
> 只输出 JSON 本身,不要任何前言、解释或 Markdown 代码块标记(不要用 \`\`\`)。
>
> JSON 格式:
> ```
> {
>   "items": [
>     {
>       "name": "食物名称",
>       "grams": 数字,
>       "kcal": 数字,
>       "protein": 数字,
>       "carbs": 数字,
>       "fat": 数字,
>       "confidence": "high" | "mid" | "low"
>     }
>   ]
> }
> ```
> 调整后的项目通常应把 confidence 提升到 "high",因为这是用户自己确认过的信息。

**输入**:`items`(原始估算清单)+ `note`(用户备注),两者拼成一段文字一起发给 AI(格式是 `原始估算:\n<JSON>\n\n备注:<note文字>`)。
**输出**:调整后的 `items[]`。

**产品意图**:用户记得的是"半碗"这种感受性描述,而不是"100 克"这种精确数字,让 AI 做这个换算比让用户自己心算再改数字要顺手。

## 4. 错误处理方式(4 个接口一致)

| 情况 | 返回 |
|---|---|
| 请求方法不是 POST | `405` `{ error: 'Method not allowed' }` |
| 缺少必填参数(如 `text` 为空) | `400` `{ error: '...' }` |
| 环境变量里没有配置 `ANTHROPIC_API_KEY` | `500` `{ error: 'ANTHROPIC_API_KEY is not set in the environment' }` |
| Claude 调用本身失败(网络、限流等) | `500` `{ error: <具体错误信息> }` |
| Claude 返回的内容解析不出合法 JSON | `500` `{ error: 'Failed to parse JSON from Claude response', rawText: <AI原始返回文字> }` |

前端拿到 500 会展示错误提示,不会让 App 崩溃;`rawText` 存在时前端也不会丢弃,方便后续手动处理或重新解析。

## 5. 单次调用的 Token 量与成本估算

**模型价格**(2026 年 8 月查证,来自 Anthropic 官方及第三方比价站,后续可能调整,建议以 Anthropic 控制台账单为准):

| | 每百万 token 价格 |
|---|---|
| 输入(input) | $3.00 |
| 输出(output) | $15.00 |

以下是按典型使用场景估算的**单次调用**量级(粗估,实际会因输入长度浮动;Chinese/CJK 文本大致按 1.3–1.8 字/token 估算):

| 接口 | 输入 token(粗估) | 输出 token(粗估,上限 1024) | 单次成本(粗估) |
|---|---|---|---|
| `parse-workout` | 系统提示词 ~380 + 用户文字 ~20-40 ≈ **400-450** | JSON 结果,通常 **100-300** | 约 $0.003-0.006(不到 1 分钱人民币) |
| `parse-meal` | 系统提示词 ~180 + 用户文字 ~20-40 ≈ **200-250** | **80-250** | 约 $0.002-0.004 |
| `analyze-photo` | 系统提示词 ~180 + 指令文字 ~10 + **图片 token**(长边 1024px 的压缩图,按 Anthropic 公式「宽×高/750」估算,约 **700-1400**)≈ **900-1600** | **100-350** | 约 $0.005-0.01 |
| `recalc-meal` | 系统提示词 ~180 + 原始清单 JSON(通常 1-3 项食物,~100-200)+ 备注文字 ~20-40 ≈ **300-420** | **80-250** | 约 $0.002-0.005 |

**结论**:单人使用场景下,每次调用成本都在 1 分人民币以内,`analyze-photo` 因为要传图片略贵一些但也在 1 分钱上下。按一天记录 3-5 次训练/饮食估算,每月成本大概率在几毛到一两块人民币这个量级。这只是基于 prompt 长度和公开定价的估算,不是账单数据,精确数字请以 Anthropic 控制台的实际用量统计为准。

## 6. 目前没有做但可以考虑的 AI 相关优化

- **Prompt Caching**:4 个接口的系统提示词是固定不变的,理论上可以用 Anthropic 的 prompt caching 把系统提示词部分的成本降低约 90%,但目前代码里没有启用(`api/_lib/claude.ts` 里没有设置 cache_control)。因为单次调用成本已经很低,这项优化目前收益不明显,值不值得做取决于以后调用频率是否显著上升。
- **流式返回(streaming)**:目前是等 AI 完整生成完 JSON 才返回,没有用流式接口,因为输出本来就是要先解析成结构化数据才能用,流式对当前场景意义不大。
