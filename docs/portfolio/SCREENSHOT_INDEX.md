# Gym 作品集截图编排（4 页版）

> **统一角标：合成演示数据 / Synthetic demo data。** 下列截图用于解释现有产品行为，不代表真人访谈、真实健康记录或线上业务指标。

## 第 1 页｜问题、目标与我的角色

**目的**：先讲清楚为什么要做，而不是堆功能。

- 核心问题：健身记录常被拆散在计划、备忘录与打卡工具中；AI 虽能降低输入成本，却可能把模型猜测误写成事实。
- 产品目标：建立 `Plan → Import → Check` 闭环，让用户从计划开始、导入当天任务、逐组确认真实完成；AI 只负责结构化，不替用户做事实决定。
- 我的角色：AI 产品设计、需求拆解、Prompt / Schema、前端实现、评测与部署排障；开发过程中使用 Claude Code / Codex 协作，但需求取舍和验收由作者完成。
- 视觉：用一张简洁流程图；本页不需要产品截图。

## 第 2 页｜核心体验：Plan → Import → Check

**主图组合**：`02-plan-templates-active-plan.png` → `04-plan-import-entrypoint.png` → `04b-workout-import-partial.png` → `04c-workout-import-complete.png`。

**辅助图**：`03-plan-editor-ordering.png`、`04a-workout-import-incomplete.png`、`01-today-checkin-calendar-panda.png`；空间足够时再放 `07a` / `07b`。

**要讲的内容**：

1. 用模板或自定义编辑形成计划，动作可排序，避免把规则生成包装成 AI。
2. 导入后所有组默认未完成，保证“计划”不会直接变成“训练事实”。
3. 用户逐组勾选；只有所有项目完成才触发成功横幅与打卡反馈。
4. Today 页把连续记录、月历和小熊猫成长放进同一反馈回路。

**推荐图注**：`计划负责给方向，Import 降低重复输入，Check 保证写入的是用户真正完成的训练。`

## 第 3 页｜AI Architecture 与 Human-in-the-loop

**主图组合**：`05-workout-ai-uncertain-edit-confirm.png` + `06-meal-ai-edit-confidence-confirm.png`。

**数据流**：`用户主动提交 → API 输入保护 → OpenAI 严格结构化输出 → 服务端校验 → 前端校验 → 可编辑预览 → 用户确认 → 浏览器本地保存`。

**要讲的内容**：

- 训练文字、饮食文字与照片识别共用“先预览、后确认”的交互原则。
- 组次、计时、重量、食物克数和营养都能在写入前修改；不确定字段使用显式提示。
- 20 条训练 V2 修复验证达到结构 20/20、边界 8/8；35 条饮食基线结构 35/35，随后 10 条重算定向回归 10/10。
- 这些是合成 API 评测，不是 20 或 35 位用户；真人编辑率、修正耗时仍未测量。

**推荐图注**：`AI 不直接写入健康记录；结构化结果必须经过双层校验和用户确认。`

## 第 4 页｜从失败证据到可公开演示

**左侧：迭代证据**

- 训练 V1 暴露模糊有氧时长与计时动作问题；V2 用 nullable 草稿和 reps / duration XOR 修复。
- 饮食基线暴露未修改食物被模型重估、置信度被抬高和名称语义别名问题；修改 Prompt 与评分器后，10 条重算回归为 10/10。
- 明确区分自动评分误报与真实产品错误，不回写历史基线。

**右侧：公开演示边界**

- 共享访问码、跨实例分钟 / 日限额、日预算预留、80% 告警与脱敏审计已实现。
- Preview / Production 缺少关键配置时 fail closed；不会退回不安全的单实例限流。
- Vercel Preview 已接通 OpenAI、Upstash、访问码与脱敏审计，可写为“受保护的 Preview 已上线并完成 401 / 200 验证”；Production 尚未发布，不能写成“已正式生产上线”，429 / 503 也不能写成线上故障注入结果。

**结尾**：下一步优先验证未知重量、自重语义与批量修改；如果无法招募真人，可把现有 8-persona 内容明确写为 AI-simulated pretest，用于生成假设，不能冒充真人访谈。
