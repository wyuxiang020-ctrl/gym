## 1. 架构层面

### 1.1 不用数据库,数据全存浏览器 localStorage 🟢
- **替代方案**:接入 Supabase / Firebase 之类的云数据库
- **为什么**:项目最初的定位就是"一个人用",不需要多设备同步、不需要账号系统。开发和部署成本都最低。
- **代价**(需要你知道):数据只存在这一台设备的这一个浏览器里,清缓存、换手机、换浏览器都会丢数据。目前用"导出/导入 JSON 文件"这个手动方式做备份(在"记录"标签页里),不是自动同步。
- 所有读写都收敛在 `src/lib/store.ts` 一个文件里,如果以后要换成真数据库,理论上只需要重写这一个文件,其他代码不用动——这是当初特意这样设计的。

### 1.2 没有账号系统 🟢
- **替代方案**:加登录注册
- **为什么**:单用户使用,加账号系统纯属增加复杂度。

### 1.3 前端不直接调用 AI,全部经过 Vercel serverless 中转 🟢
- **替代方案**:前端直接拿着 API key 调用 OpenAI
- **为什么**:API key 写在前端代码里任何人打开浏览器都能看到,会被盗用产生费用。这是安全上的硬性要求,不是可选项。

### 1.4 没有用 React Router,单页 + state 切换标签 🟡
- **替代方案**:用 `react-router` 做真正的 URL 路由,每个标签对应一个 URL
- **为什么这样选**:应用整体很轻,5 个标签之间没有"分享某个具体页面链接"的需求,少一个依赖。
- **代价**:刷新页面会回到默认标签(今天),浏览器前进/后退按钮对标签切换无效。如果以后想要"分享某一天的记录"之类的链接功能,需要重新引入路由。

### 1.5 外部和备份数据必须做运行时校验 🟢
- **替代方案**:只依赖 TypeScript 类型断言,默认导入文件和 AI 返回一定符合接口。
- **为什么**:TypeScript 不会在浏览器运行时验证 JSON。合法但结构错误的备份曾可能覆盖本地数据并导致刷新后白屏,AI 也可能返回语法正确但字段不完整的对象。现在备份在覆盖前校验结构和数值范围,AI 结果在服务端和前端各校验一次;不合格的数据会被拒绝并保留用户原输入。
- **恢复策略**:有效备份仍需用户二次确认,替换前自动下载当前数据的时间戳安全副本。若现有 `gym-data-v1` 已损坏或与当前模型不兼容,App 启动时优先显示可操作的恢复页,后续普通写入暂停,原始 JSON 仍可原样导出；导入成功后父级状态即时重载。不能让用户被错误带到建档页,也不能把读取失败悄悄降级为空数据后再覆盖。
- **文件边界**:记录页在读取 JSON 前先拒绝超过 10 MB 的文件，避免把明显异常的大文件交给浏览器解析；通过文件大小检查仍不代表内容有效，后续结构校验、确认和替换前备份照常执行。

### 1.6 AI 服务端支持显式本地代理,但不写死代理地址 🟢
- **替代方案**:把当前电脑的 `127.0.0.1:7897` 直接写进 OpenAI 客户端,或假设浏览器代理会自动覆盖 Node。
- **为什么**:实测浏览器可以打开 OpenAI 控制台,但 Node 直连 `api.openai.com:443` 超时;通过本机代理端口则能到达 OpenAI。用环境变量配置代理可以修复本地联调,同时避免线上部署错误依赖开发者电脑的地址。

### 1.7 固定模型日期快照，并把正式评测绑定到源码快照 🟢
- **替代方案**:长期使用会自动变化的模型别名,只记录一个总通过率而不保存数据集、原始响应和当时源码。
- **为什么**:AI 行为会随模型版本和 Prompt 变化。当前固定为 `gpt-5-mini-2025-08-07`，V1 正式评测还记录了数据集、Prompt/source、实际模型、工作区、Response ID、usage 和原始响应哈希，并保存当时的关键源码快照。这样后续 V2 变更不会改写历史基线。OpenAI 官方模型页也说明 snapshot 用来锁定版本；若更换模型，需建立新基线。
- **版本隔离**:`eval:workout:v1` 保留历史合约，旧 `eval:workout` 只是 V1 兼容别名；V2 有独立的 20 条数据集、Rubric 和运行器。当前 V2 离线证据为 20 条用例 / 47 项评分器自检通过且 `network_requests=0`，另有 14/14 AI 运行时合约固定样例检查；离线检查不是模型质量成绩。
- **中断运行边界**:V2 首次正式尝试 `2026-09-05-openai-regression-v2` 在 WO-14 后中止，只保留 14 次请求的 partial；前 13 条有 Response ID / usage，已知 18,302 token、估算 $0.013075 USD，WO-14 usage 和整次尝试成本未知。它不能产生通过率，也不能代表随后改变过的 Schema、Prompt 和校验代码。下一次完整运行必须另获授权并使用新 Run ID 从头执行，不能续写 partial。
- **网络中断边界**:第二次尝试 `2026-09-06-openai-regression-v2-r2` 在第 4 题遇到无 Response ID 的连接错误并停止；前三题已知 4,616 token、估算 $0.002790 USD，第 4 题计费状态不可核实。根因是本机直连路径异常，且已有本地代理配置因旧环境加载条件未进入函数进程。修复后会补载缺失代理值，但仍不续写 partial，也不把无密钥 HTTP 401 连通性测试称作模型回归。
- **完整 V2 证据**:`2026-09-06-openai-regression-v2-r3` 完成 20/20 次顺序请求且无重试，得到核心 12/12 direct、字段 182/182、边界 7/8、结构 20/20；20 条 Response ID/响应哈希唯一，人工复核改分 0 条。WO-13 暴露“只缺重量时不应丢掉已知组次”，Prompt 在结果冻结后补充该规则，后续必须用新 Run ID 重新验证，不能回写 r3 分数。
- **边界**:V1 与 V2 都只是 20 条合成、单轮、API parse-only 测试，不能代表 20 位用户、线上 SLA 或健康结果；真人编辑率等仍是 `NOT_MEASURED`。

### 1.8 AI API 先做输入边界与实例内限流 🟢
- **替代方案**:把任意大小、任意类型的请求直接转发给模型，或把当前内存计数器宣传成完整防滥用系统。
- **为什么**:文字、图片和重算清单会产生费用，也可能消耗函数内存。现在统一限制 POST + `application/json`、JSON 正文、字段长度和数组数量，并设置 `Cache-Control: no-store`；每 IP 每分钟最多 30 次。无付费 guard 检查当前 10/10，全部样例在模型调用前按预期拒绝。
- **代价 / P1**:限流只存在于当前 Serverless 实例内，冷启动会重置且多实例不共享。项目仍没有用户鉴权；公开给多用户前必须补持久化跨实例共享限流、预算告警和调用审计。10/10 guard 不能替代这些能力。

### 1.9 在 AI 提交入口明确第三方数据范围 🟢
- **替代方案**:只在长文档里写隐私说明，或让用户误以为“业务数据存在 localStorage”等于 AI 输入也完全不离开设备。
- **为什么**:训练/饮食文字、餐食数据和压缩图片在用户主动调用 AI 时会发送给 OpenAI。训练和饮食界面现在都在提交入口附近说明发送范围，并强调结果核对确认后才写入本地。`store: false` 只表示本应用不要求保存可再次获取的 Response 状态，不被表述成第三方数据政策保证。

### 1.10 不把图片扩展名、文件头或浏览器压缩当作完整安全校验 🟢
- **替代方案**:只核对 MIME/魔数后把原 Base64 直接发给模型，或只依赖前端把图片缩到 1024px。
- **为什么**:截断文件、伪造文件头、超大像素图和多帧图片仍可能通过浅层检查并消耗服务端/模型资源。服务端先把 Base64 解码后的输入文件限制为 3 MiB，再用生产依赖 `sharp` 0.35 以严格告警策略完整解码，限制单边 4096、总像素 1600 万和单帧，随后自动旋转、最长边 1024、铺白、转 sRGB、去元数据并以质量 80 重编码 JPEG。只有规范化结果会发送给 OpenAI。
- **代价**:Serverless 包体、冷启动和图片处理 CPU/内存成本会增加；因此 `sharp` 必须保留为生产依赖并在目标部署环境验证原生二进制兼容性。

### 1.11 已取得模型 Response 的输出失败返回 422 并保留证据 🟢
- **替代方案**:把空输出、JSON 解析失败和运行时结构失败一律包装成无元数据的 500，或因为调用已经付费就勉强接收非法结果。
- **为什么**:V2 首次尝试的 WO-14 已产生模型输出，但旧 500 路径丢失了 Response ID 与 usage，既不能审计成本，也让评测器无法区分“模型答错”和“网络没拿到结果”。现在 4 个 AI 接口在已经取得可核实 Response 后，把空输出/JSON 解析失败返回为 422 + `MODEL_OUTPUT_PARSE_FAILED`，把运行时结构失败返回为 422 + `MODEL_OUTPUT_VALIDATION_FAILED`；两者都带可获得的 `rawText` 和 `meta`，同时继续拒绝写入非法数据。
- **边界**:尚未取得可核实 Response 的网络、鉴权、额度或其他供应商异常仍为 500，不保证有 `meta`。V2 runner 仅把“422 且有 Response ID”作为已调用、可计分的该题失败并继续；网络/上游、其他非成功 HTTP 或缺少证据时中止。SDK 不自动重试、超时 110 秒，runner 超时 120 秒。

## 2. 训练相关

### 2.1 训练/有氧消耗热量用 MET 公式计算,不用 AI 估算 🟢
- **替代方案**:让 AI 在解析自然语言的同时顺便给出热量估算
- **为什么**:这是明确要求——公式确定、免费、瞬时;AI 估算同样的东西反而不稳定,还要多花 token。详见 `AI_FEATURES.md` 第 3.1 节。

### 2.2 训练计划用规则生成,不用 AI 生成 🟢
- **替代方案**:调 AI 直接生成一份训练计划
- **为什么**:同上,规则生成更确定、可解释、免费、瞬间完成。

### 2.3 训练计划模板固定 5 套,写死在代码里 🟡
- **替代方案**:接入某个健身计划数据库或用 AI 按需生成更多样的模板
- **为什么这样选**:5 套(新手全身三日、上下肢四分化、推拉腿三分化、Arnold 六分化、五分化)覆盖了从新手到有经验用户的常见诉求,是编写时按健身圈公认的经典编排整理的,不是某个官方数据源。
- 🔴 **需要你补充**:如果这 5 套模板的动作选择、组数次数区间不符合你的实际训练偏好,需要你具体指出改哪里——这块内容目前没有专业教练审核过。

### 2.4 动作要领用文字卡片 + 用户自填视频链接,没有接入真实教学视频 🟢
- **替代方案**:嵌入 B 站/YouTube 搜索结果,或者生成动作演示视频
- **为什么**:无法保证搜索出来的第三方视频内容准确、可用、不侵权,与其提供一个可能失效或误导的链接,不如提供确定可靠的文字要领,并留一个入口让用户自己填一个他信任的直链视频地址,用原生 `<video>` 播放,不跳转到别的平台。
- **代价**:目前没有任何真实动作视频/图片,只有文字要领和一个抽象的动作方向示意动画。

### 2.5 训练计划拖动排序用 Pointer Events 手写,不用第三方拖拽库 🟢
- **替代方案**:用 `react-beautiful-dnd`、`dnd-kit` 等成熟库
- **为什么**:最初用的是 HTML5 原生 `draggable` 属性,后来发现这个 API 在 iOS Safari 触屏上基本不生效,是用户反馈"没法调整顺序"的根本原因。改成手写 Pointer Events 版本是为了避免引入较重的第三方依赖,同时确保触屏兼容。

### 2.6 训练容量和热量只统计已勾选完成的组 🟢
- **替代方案**:计划一经导入就按预填的重量和次数计入容量与热量。
- **为什么**:导入代表计划,勾选才代表实际完成。计划中的力量组和有氧都以待完成状态进入当天记录；有氧只有选好支持的项目并勾选完成后才计算热量。未完成内容如果提前进入月历热力图、历史容量、打卡和宠物成长,会把计划数据伪装成训练成果。计时动作不进入 `weight × reps` 容量。

### 2.7 重复导入计划时不自动覆盖已有记录 🟢
- **替代方案**:无提示地重复追加,或直接用计划内容覆盖当天同名动作/同类型同分钟的有氧。
- **为什么**:无提示追加容易产生重复记录;自动覆盖则可能删掉用户已经完成和修改过的真实内容。检测到重复力量动作或有氧时,界面要求用户明确选择“跳过重复项目”或“仍然追加全部”,兼顾防误触和一天两练。
- **有氧来源标记**:计划有氧写入 `计划来源:<原类型> <分钟>分钟`，即使用户把通用计划改选成具体项目，重复导入时仍能按原计划识别；用户主动“清除提示”后该标记也会被删除，此时只按当前类型 + 分钟判断。

### 2.8 计时力量组单独存秒数，模糊有氧先作为不可保存草稿 🟢
- **替代方案**:把平板支撑的“30 秒”借用 `reps: 30` 保存，或给“跑了一会儿”填 `minutes: 1` 之类的最小占位值。
- **为什么**:V1 正式评测的 WO-18 和 WO-15 证明这两种占位会把模型限制伪装成用户事实。V2 为 `StrengthSet` 增加整数 `durationSeconds`，并要求它与整数 `reps` 二选一；服务端、AI 预览保存和本地备份校验都执行相同整数约束。手动记录和 AI 预览都允许用户逐组切换次数/计时，AI 预览还可新增组。AI 有氧预览允许 `minutes: null`，但必须由用户补成有效时长才能保存。计时组不进入 `weight × reps` 的训练容量。
- **证据边界**:旧 Schema 曾允许 `reps` 与 `durationSeconds` 同时为 `null`，首次 V2 尝试因此在 WO-14 中止，WO-15 / WO-18 根本没有运行。修复后 Schema 用嵌套 `anyOf` 严格实现 XOR，Prompt 要求缺组数或次数/时长时返回 `sets: []`，运行时 validator 与 Schema 的精确键集合一致；完整 r3 已证明 WO-14、WO-15、WO-18 在该次单轮合成输入上通过，但不能外推为真人或线上表现。

### 2.9 AI 同名动作在写入前要求追加 / 替换 / 返回编辑 🟢
- **替代方案**:解析成功后直接追加到同名动作，或直接覆盖当天真实记录。
- **为什么**:追加适合补录新完成组，替换适合纠正整组识别，返回编辑用于发现识别错误；任何单一默认值都可能造成重复或数据丢失。现在检测到同名动作时整批结果先暂停，用户明确选择后才写入。预览同时开放有氧距离、平均心率等关键字段，减少为了修正模型结果而被迫重跑。
- **来源与提示**:把 AI 组数追加到手动动作时，来源改为 `mixed` 并显示“AI辅助”；替换后则标为纯 AI。力量和有氧的 `note` / `uncertain` 写入后继续显示，只有用户点“已处理，清除提示”才清空，避免不确定性在确认瞬间消失。

### 2.10 计划与 AI 批量导入按整天预检并一次写入 🟢
- **替代方案**:在循环里逐项调用 `addStrengthEntry()` / `addCardioEntry()`，前几项成功后才发现后续内容越界。
- **为什么**:逐项写入会留下难以解释的“半次导入”。现在两条批量路径都先在内存构造完整结果，检查单动作 50 组、当天 200 个力量动作和 100 个有氧项目等上限，再通过 `replaceDayLog()` 对完整 `DayLog` 做运行时校验和单次 `localStorage` 写入；任一步失败时当天记录保持原样。
- **范围说明**:这里的“原子化”指应用内不会主动逐项部分写入，不是数据库事务或跨设备同步保证。

### 2.11 计划的次数/计时格式在导入边界显式解析 🟢
- **替代方案**:凡是出现数字都取第一个数字当次数，或无法理解时默认为 8 次。
- **为什么**:`repRange` 历史上是自由文本，既有 `8-12`，也有 `30秒`、`每组30秒`、`30-45秒`、`0.5分钟/组`。次数解析只取逗号/分号前的目标段并做锚定匹配，计时解析则要求整个字符串匹配；已识别时长会换算、四舍五入为整数秒。`RPE 8`、`3×10`、`AMRAP`、`8-10 RPE8` 等没有独立明确目标的写法不再猜成 8、3 或 10 次，而是保留原文提示并生成空组，要求用户修正。单个动作最多导入 20 组。

## 3. 饮食相关

### 3.1 蛋白质/脂肪/碳水目标怎么算的 🟡

| 目标 | 蛋白质系数(每 kg 体重) | 说明 |
|---|---|---|
| 增肌 | 1.9 g | 常见推荐区间 1.6-2.2,取中值 |
| 减脂 | 2.0 g | 常见推荐区间 1.8-2.2,取中值 |
| 维持 | 1.4 g | 常见推荐区间 1.2-1.6,取中值 |

脂肪目标 = 总热量目标 × 25%(常见推荐区间 20-30%,取中值)÷ 9;碳水目标 = 剩余热量 ÷ 4。

- **为什么这样选**:这几个系数都是营养学里常被引用的推荐区间,代码里取的是区间中值,不是某个个性化算法的结果。
- 🔴 **需要你补充**:如果你有更具体的营养师建议或个人偏好,这几个系数是最值得先调整的地方(在 `src/lib/nutritionTargets.ts` 里)。

### 3.2 热量目标下限 = 不低于 BMR 🟢
- **为什么**:明确要求的安全边界,任何情况下不建议低于基础代谢。

### 3.3 蔬菜目标固定 400g/天,不随体重变化 🟢
- **为什么**:参照中国居民膳食指南的通用建议(300-500g/天),这个量级本身跟体重关系不大,所以没有做个性化。

### 3.4 "菜谱搭配"功能默认给 150g,不是自动按缺口算 🟡
- **替代方案**(最初版本就是这么做的):自动按当天蛋白质缺口反算需要吃多少克
- **为什么改成固定默认值**:自动算出来的克数经常不现实(比如一次要吃 640g 鸡胸肉),改成一个正常单次分量的默认值,再让用户自己用加减按钮调整,更符合实际做菜的量。这是根据你的反馈调整的。

### 3.5 食材营养数据(每 100g 含量)是通用估算值,不是精确营养数据库 🟢
- **代价**:`src/lib/nutritionTargets.ts` 和 `src/lib/recipeIngredients.ts` 里的数字(比如"鸡胸肉每 100g 含 23g 蛋白质")是常识性估算,不是查权威数据库得出的,具体品牌/部位/做法会有偏差。

### 3.6 AI 重算必须由用户确认后写入 🟢
- **替代方案**:AI 返回后直接覆盖原餐食。
- **为什么**:重算仍然是估算,直接覆盖会让用户丢失可比较的原始数据。现在先显示原/新热量差异和可编辑清单,确认才替换,取消不改原记录。

### 3.7 修改食物克数时同比例缩放营养数据 🟡
- **替代方案**:只改变克数,其余字段保持不动,或者每次修改都重新调用 AI。
- **为什么这样选**:对同一种食物,短时间内按份量线性缩放是成本最低且容易理解的近似;它避免克数和营养值明显矛盾,也不产生额外 API 调用。用户仍能单独修正各营养字段。

### 3.8 AI 饮食结果和最终保存使用分层上限 🟢
- **替代方案**:允许模型或编辑器返回任意数量、无限大的食物数据，或者把 API 的 30 项限制误当成用户最终只能保存 30 项。
- **为什么**:模型响应与重算请求最多 30 项，先控制 token、正文和异常数组；用户编辑预览或手动记录时新保存要求每餐 1–100 项。两层都限制名称 120 字符、克数 / kcal 100,000、单项宏量营养素 10,000，新确认保存还要求克数、热量或三项宏量营养素中至少一个数值大于 0。备份导入为兼容历史数据允许每餐 0–100 项和旧全零项，但仍执行数值上限。

## 4. 打卡与游戏化

### 4.1 打卡定义可以由用户自己设置(三选一) 🟢
- **为什么**:明确要求,不同人对"算不算坚持"的标准不一样。
- **完成口径**:`workout` / `workout_and_meal` 与训练页完成提示复用 `hasCompletedWorkout()`：至少有一组 `done=true` 且整数次数/持续秒数为正，或有 `done !== false` 的正时长有氧。计划导入的 `done=false` 不满足条件；旧有氧没有该字段时按已完成兼容。训练页“今日训练已计入档案”还会额外要求当天所有力量组和有氧均完成，避免在仍有待完成项目时提前庆祝。

### 4.2 打卡断掉不做惩罚性设计 🟢
- **为什么**:明确要求——断了就是重新从 1 开始,不弹"连续记录中断了"这种提示,月历上留白就行。

### 4.3 宠物(小熊猫)升级门槛、打卡连续天数勋章门槛 🟡
- 宠物等级门槛:0 / 1,000 / 5,000 / 20,000 / 50,000(累计训练容量,单位 kg·次)
- 打卡勋章门槛:3 / 7 / 14 / 30 / 100 天
- **为什么这样选**:这些数字是凭经验估的"大致对应几周到几个月的持续训练",没有做过实际用户数据校准。
- 🔴 **需要你补充**:用一段时间之后,如果升级/解锁速度感觉太快或太慢,这些门槛(在 `src/lib/pet.ts` 和 `src/components/checkin/StreakCard.tsx` 里)是最直接的调整点。

### 4.4 宠物每天只能投喂一次 🟡
- **替代方案**:不限制投喂次数
- **为什么这样选**:让"投喂"这个动作更像一个每日仪式,而不是一个可以无限点击的按钮,增加一点"精致感"。这是根据你的反馈加的限制,门槛数值(每天一次)本身没有和你反复确认过是不是最合适的频率。

### 4.5 手动累计值也必须有硬上限 🟢
- **为什么**:加减按钮和长按输入同样可能被误触。力量记录的重量 / 次数 / 单组计时分别钳制在 1,000 kg、1,000 次、86,400 秒；单日饮水最多 20,000 ml，单次自定义加水输入最多 5,000 ml。上限同时存在于输入界面和本地运行时校验，避免异常值污染历史与汇总。
