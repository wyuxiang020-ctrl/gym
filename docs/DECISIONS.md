- 🟡 **实现时的判断**:没有人明确要求这个具体数值/方案,是实现过程中做的选择,建议你确认是否符合预期

## 1. 架构层面

### 1.1 不用数据库,数据全存浏览器 localStorage 🟢
- **替代方案**:接入 Supabase / Firebase 之类的云数据库
- **为什么**:项目最初的定位就是"一个人用",不需要多设备同步、不需要账号系统。开发和部署成本都最低。
- **代价**(需要你知道):数据只存在这一台设备的这一个浏览器里,清缓存、换手机、换浏览器都会丢数据。目前用"导出/导入 JSON 文件"这个手动方式做备份(在"记录"标签页里),不是自动同步。
- 所有读写都收敛在 `src/lib/store.ts` 一个文件里,如果以后要换成真数据库,理论上只需要重写这一个文件,其他代码不用动——这是当初特意这样设计的。

### 1.2 没有账号系统 🟢
- **替代方案**:加登录注册
- **为什么**:单用户使用,加账号系统纯属增加复杂度。

### 1.3 前端不直接调用 AI,全部经过 Vercel serverless 中转 🟢
- **替代方案**:前端直接拿着 API key 调用 Anthropic
- **为什么**:API key 写在前端代码里任何人打开浏览器都能看到,会被盗用产生费用。这是安全上的硬性要求,不是可选项。

### 1.4 没有用 React Router,单页 + state 切换标签 🟡
- **替代方案**:用 `react-router` 做真正的 URL 路由,每个标签对应一个 URL
- **为什么这样选**:应用整体很轻,5 个标签之间没有"分享某个具体页面链接"的需求,少一个依赖。
- **代价**:刷新页面会回到默认标签(今天),浏览器前进/后退按钮对标签切换无效。如果以后想要"分享某一天的记录"之类的链接功能,需要重新引入路由。

## 2. 训练相关

### 2.1 训练/有氧消耗热量用 MET 公式计算,不用 AI 估算 🟢
- **替代方案**:让 AI 在解析自然语言的同时顺便给出热量估算
- **为什么**:这是明确要求——公式确定、免费、瞬时;AI 估算同样的东西反而不稳定,还要多花 token。详见 `AI_FEATURES.md` 第 3.1 节。

### 2.2 训练计划用规则生成,不用 AI 生成 🟢
- **替代方案**:调 AI 直接生成一份训练计划
- **为什么**:同上,规则生成更确定、可解释、免费、瞬间完成。

### 2.3 训练计划模板固定 5 套,写死在代码里 🟡
- **替代方案**:接入某个健身计划数据库或用 AI 按需生成更多样的模板
- **为什么这样选**:5 套(新手全身三日、上下肢四分化、推拉腿三分化、Arnold 六分化、五分化)覆盖了从新手到有经验用户的常见诉求,是编写时按健身圈公认的经典编排整理的,不是某个官方数据源。
- 🔴 **需要你补充**:如果这 5 套模板的动作选择、组数次数区间不符合你的实际训练偏好,需要你具体指出改哪里——这块内容目前没有专业教练审核过。

### 2.4 动作要领用文字卡片 + 用户自填视频链接,没有接入真实教学视频 🟢
- **替代方案**:嵌入 B 站/YouTube 搜索结果,或者生成动作演示视频
- **为什么**:无法保证搜索出来的第三方视频内容准确、可用、不侵权,与其提供一个可能失效或误导的链接,不如提供确定可靠的文字要领,并留一个入口让用户自己填一个他信任的直链视频地址,用原生 `<video>` 播放,不跳转到别的平台。
- **代价**:目前没有任何真实动作视频/图片,只有文字要领和一个抽象的动作方向示意动画。

### 2.5 训练计划拖动排序用 Pointer Events 手写,不用第三方拖拽库 🟢
- **替代方案**:用 `react-beautiful-dnd`、`dnd-kit` 等成熟库
- **为什么**:最初用的是 HTML5 原生 `draggable` 属性,后来发现这个 API 在 iOS Safari 触屏上基本不生效,是用户反馈"没法调整顺序"的根本原因。改成手写 Pointer Events 版本是为了避免引入较重的第三方依赖,同时确保触屏兼容。

## 3. 饮食相关

### 3.1 蛋白质/脂肪/碳水目标怎么算的 🟡

| 目标 | 蛋白质系数(每 kg 体重) | 说明 |
|---|---|---|
| 增肌 | 1.9 g | 常见推荐区间 1.6-2.2,取中值 |
| 减脂 | 2.0 g | 常见推荐区间 1.8-2.2,取中值 |
| 维持 | 1.4 g | 常见推荐区间 1.2-1.6,取中值 |

脂肪目标 = 总热量目标 × 25%(常见推荐区间 20-30%,取中值)÷ 9;碳水目标 = 剩余热量 ÷ 4。

- **为什么这样选**:这几个系数都是营养学里常被引用的推荐区间,代码里取的是区间中值,不是某个个性化算法的结果。
- 🔴 **需要你补充**:如果你有更具体的营养师建议或个人偏好,这几个系数是最值得先调整的地方(在 `src/lib/nutritionTargets.ts` 里)。

### 3.2 热量目标下限 = 不低于 BMR 🟢
- **为什么**:明确要求的安全边界,任何情况下不建议低于基础代谢。

### 3.3 蔬菜目标固定 400g/天,不随体重变化 🟢
- **为什么**:参照中国居民膳食指南的通用建议(300-500g/天),这个量级本身跟体重关系不大,所以没有做个性化。

### 3.4 "菜谱搭配"功能默认给 150g,不是自动按缺口算 🟡
- **替代方案**(最初版本就是这么做的):自动按当天蛋白质缺口反算需要吃多少克
- **为什么改成固定默认值**:自动算出来的克数经常不现实(比如一次要吃 640g 鸡胸肉),改成一个正常单次分量的默认值,再让用户自己用加减按钮调整,更符合实际做菜的量。这是根据你的反馈调整的。

### 3.5 食材营养数据(每 100g 含量)是通用估算值,不是精确营养数据库 🟢
- **代价**:`src/lib/nutritionTargets.ts` 和 `src/lib/recipeIngredients.ts` 里的数字(比如"鸡胸肉每 100g 含 23g 蛋白质")是常识性估算,不是查权威数据库得出的,具体品牌/部位/做法会有偏差。

## 4. 打卡与游戏化

### 4.1 打卡定义可以由用户自己设置(三选一) 🟢
- **为什么**:明确要求,不同人对"算不算坚持"的标准不一样。

### 4.2 打卡断掉不做惩罚性设计 🟢
- **为什么**:明确要求——断了就是重新从 1 开始,不弹"连续记录中断了"这种提示,月历上留白就行。

### 4.3 宠物(小熊猫)升级门槛、打卡连续天数勋章门槛 🟡
- 宠物等级门槛:0 / 1,000 / 5,000 / 20,000 / 50,000(累计训练容量,单位 kg·次)
- 打卡勋章门槛:3 / 7 / 14 / 30 / 100 天
- **为什么这样选**:这些数字是凭经验估的"大致对应几周到几个月的持续训练",没有做过实际用户数据校准。
- 🔴 **需要你补充**:用一段时间之后,如果升级/解锁速度感觉太快或太慢,这些门槛(在 `src/lib/pet.ts` 和 `src/components/checkin/StreakCard.tsx` 里)是最直接的调整点。

### 4.4 宠物每天只能投喂一次 🟡
- **替代方案**:不限制投喂次数
- **为什么这样选**:让"投喂"这个动作更像一个每日仪式,而不是一个可以无限点击的按钮,增加一点"精致感"。这是根据你的反馈加的限制,门槛数值(每天一次)本身没有和你反复确认过是不是最合适的频率。
